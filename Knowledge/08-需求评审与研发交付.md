# 需求评审与研发交付

> Requirement Review & Development Handoff  
> Version: 1.0

---

# 1. 文档目的

本文档定义 AI 产品经理如何在 PRD 基本完成后，组织和执行：

* 需求自检
* 多角色需求评审
* Red Team 式质疑
* 问题分级
* 缺口修复
* Development Readiness 判断
* 研发交付
* 需求拆分
* 研发问答
* 变更控制
* 上线前需求确认

本阶段的核心目标不是：

> “把 PRD 发给研发。”

而是：

> **确认需求已经达到足够清晰、完整、一致、可实现、可测试的程度，再正式进入研发。**

最终应能够明确给出：

> **READY FOR DEVELOPMENT**

或：

> **NOT READY FOR DEVELOPMENT**

---

# 2. 前置条件

进入正式需求评审前，原则上应具备：

* PRD 已形成
* MVP Scope 已明确
* 核心 User Stories 已明确
* 功能架构已明确
* 核心业务流程已闭环
* 关键 Business Rules 已定义
* 必要 State Machine 已定义
* Permission 已定义
* Exception / Edge Case 已基本覆盖
* 核心 UX / Wireframe 已形成
* Acceptance Criteria 已基本可测试
* 关键依赖已识别
* Open Questions 已记录

如果上述关键内容大量缺失：

> 不应直接进入正式研发评审。

应返回对应阶段补齐。

---

# 3. 需求评审的真正目的

需求评审不是：

> 产品经理讲一遍 PRD，研发听完说“收到”。

真正的评审应该验证：

```text
需求是否正确
↓
逻辑是否完整
↓
范围是否清晰
↓
规则是否一致
↓
异常是否覆盖
↓
技术上是否可落地
↓
测试上是否可验证
↓
是否存在重大风险
```

---

# 4. 评审原则

## 4.1 Challenge, Not Approve

评审的目标不是默认通过。

而是主动寻找：

* 不合理需求
* 逻辑漏洞
* 隐含假设
* Scope Creep
* 冲突规则
* 极端场景
* 技术风险
* 不可测试内容

---

## 4.2 Evidence Over Authority

“老板要求”不意味着逻辑可以不完整。

“产品经理决定”也不代表不能质疑。

关键问题仍应回答：

> 为什么？

> 有什么证据？

> 有什么代价？

---

## 4.3 Fix Before Build

重大问题应尽量在研发前解决。

因为：

```text
需求阶段发现问题
<
设计阶段发现问题
<
开发阶段发现问题
<
测试阶段发现问题
<
线上发现问题
```

越晚发现，成本通常越高。

# 5. Review Inputs

正式评审建议准备：

```text
PRD

Low-Fi / High-Fi Prototype

User Story Map

Product Functional Architecture

Core Business Flows

Feature Specifications

Business Rules

State Machine

Permission Matrix

Acceptance Criteria

Dependencies

Risks

Open Questions

Decision Log
```

不是所有项目都必须有全部文档。

应根据复杂度裁剪。

---

# 6. 评审角色

建议从以下角色视角进行检查：

* Product
* UX / UI
* Frontend
* Backend
* Architect
* QA
* Security
* Data
* Operations
* Business

实际项目根据团队情况选择。

---

# 7. Product Review

产品视角重点检查：

```text
为什么做？

用户是谁？

核心问题是否成立？

目标是否明确？

Scope 是否清楚？

MVP 是否过大？

有没有偏离核心价值？

功能之间是否矛盾？
```

---

# 8. 产品价值检查

对每个核心 Feature 询问：

```text
它解决哪个问题？

服务哪个用户？

支撑哪个 User Story？

为什么必须现在做？

不做会怎样？
```

如果无法回答：

> 需求价值可能不足。

---

# 9. Scope Review

检查：

* 是否偷偷新增 Feature
* 是否出现“顺便做一下”
* 是否为了未来扩展提前建设
* 是否存在当前版本并不需要的后台能力
* 是否与 Out of Scope 冲突

---

# 10. MVP Review

重点判断：

> 当前版本是否仍然是最小完整价值闭环？

如果某需求：

> 不影响核心价值验证

却成本很高，应考虑移到：

> Next / Later。

---

# 11. UX Review

UX 视角检查：

* 用户知道下一步吗
* 信息层级是否合理
* 核心流程是否过长
* 是否重复输入
* 是否有 Dead End
* Loading 是否明确
* Empty 是否明确
* Error 是否明确
* No Permission 是否明确

---

# 12. Interaction Consistency Review

检查：

* 相同操作是否使用相同行为
* 删除逻辑是否一致
* 保存行为是否一致
* Modal 是否一致
* Back 行为是否一致
* Error 反馈是否一致

---

# 13. Frontend Review

前端视角重点关注：

* 页面状态是否明确
* 数据加载时怎么表现
* 表单校验逻辑
* 按钮 Enabled / Disabled 条件
* 权限对页面的影响
* 状态变化后的 UI 更新
* 长任务表现
* Partial Success
* Responsive Requirement

---

# 14. Frontend State Review

每个核心页面主动检查：

```text
Default

Loading

Empty

Success

Error

Disabled

No Permission
```

不要求机械全部存在。

但必须主动判断。

---

# 15. Backend Review

后端视角重点检查：

* Business Rules 是否明确
* 状态机是否合理
* 数据边界是否明确
* 权限是否明确
* 重复提交如何处理
* 并发如何处理
* 第三方失败怎么办
* Fallback 是什么
* 是否存在无法保持一致的业务要求

---

# 16. Business Rule Review

对规则逐条问：

```text
条件明确吗？

结果明确吗？

边界明确吗？

是否有冲突规则？

失败后状态是什么？

规则来源是什么？
```

---

# 17. State Machine Review

重点检查：

* 状态是否完整
* 状态是否互斥
* 状态是否有歧义
* Transition 是否明确
* Forbidden Transition 是否明确
* Terminal State 是否合理
* 是否允许回退
* 回退权限是什么

---

# 18. Permission Review

重点检查：

```text
谁
能对
什么资源
做什么
在什么条件下
```

不仅检查菜单权限。

还要检查：

* Action Permission
* Resource Scope
* State-based Permission
* Ownership

---

# 19. Concurrency Review

对高风险操作主动考虑：

```text
两个用户同时操作怎么办？

两个管理员同时审核怎么办？

库存只剩 1 个怎么办？

用户页面数据已过期怎么办？
```

产品经理不必定义锁实现。

但必须明确：

> 期望业务结果。

---

# 20. Idempotency Review

特别关注：

* 创建订单
* 支付
* 退款
* 提交审核
* 发券
* 发消息
* 批量操作

原则：

> 同一个业务动作被重复触发，不应产生不可接受的重复业务结果。

---

# 21. Third-Party Dependency Review

对于：

* 支付
* 短信
* 邮件
* 地图
* AI Provider
* 第三方登录
* 外部 API

需要检查：

```text
失败怎么办？

超时怎么办？

返回未知状态怎么办？

有没有 Fallback？

是否阻塞核心业务？
```

---

# 22. Architect Review

架构视角不负责决定产品需求。

但可以指出：

* 极高技术复杂度
* 系统耦合
* 数据一致性风险
* 不合理实时性要求
* 扩展性冲突
* 第三方限制
* 不可接受技术成本

---

# 23. Product 与 Architecture 的协作

产品负责：

```text
What

Why

Expected Behavior

Acceptance
```

架构负责：

```text
How

System Design

Technical Trade-off
```

但如果技术约束改变用户体验：

> 必须回到产品层重新决策。

---

# 24. 技术不可行不是直接删除需求

当研发说：

> “这个很难做。”

需要进一步分析：

```text
难在哪里？

成本多大？

风险是什么？

有没有替代方案？

能否降低 Scope？

能否改变体验？
```

最后形成 Product Decision。

---

# 25. QA Review

QA 视角核心问题：

> 我能不能根据文档明确写出测试 Case？

重点检查：

* Positive Case
* Negative Case
* Boundary Case
* State Transition
* Permission
* Exception
* Retry
* Duplicate Submit
* Partial Failure

---

# 26. Testability Review

如果需求写：

> “体验要流畅。”

QA 无法测试。

应该转化为：

* 明确行为
* 明确规则
* 必要指标

---

# 27. Acceptance Criteria Review

每个核心 Feature 至少应检查：

```text
成功条件

失败条件

边界条件
```

高风险功能再检查：

```text
权限

状态

重复

并发
```

---

# 28. Security Review

涉及以下场景时考虑安全评审：

* 登录
* 权限
* 支付
* 隐私
* 文件上传
* 敏感数据
* 导出
* 管理后台
* AI 数据输入

---

# 29. Security Questions

产品层可以检查：

```text
谁可以看到？

谁可以导出？

谁可以修改？

敏感字段是否脱敏？

高风险操作是否审计？

删除是否真的删除？

AI 是否处理敏感信息？
```

---

# 30. Privacy Review

如果涉及：

* 聊天内容
* 电话
* 地址
* 身份信息
* 行为数据
* 企业数据

需要明确：

* 收集什么
* 为什么收集
* 谁可访问
* 保存多久
* 能否删除
* 能否导出

---

# 31. Data Review

数据视角重点检查：

* 指标是否可测
* Event 是否定义
* 数据来源是否明确
* Success Metric 是否能被计算
* 埋点是否遗漏关键行为

---

# 32. Analytics Review

不要变成：

> 所有按钮全部埋点。

重点围绕：

```text
核心行为

核心转化

失败原因

留存

价值验证
```

---

# 33. Operations Review

如果产品需要人工运营：

必须确认：

```text
谁处理？

在哪里处理？

处理什么？

需要什么权限？

异常如何升级？

如何追踪？
```

---

# 34. 不要忽略后台流程

很多产品只设计用户端：

```text
用户提交申请
↓
完成
```

但实际上：

```text
用户提交
↓
运营处理
↓
审核
↓
异常处理
↓
用户反馈
```

后台流程不完整，产品仍然无法运转。

---

# 35. Business Review

业务侧重点：

* 商业目标是否匹配
* 规则是否符合业务政策
* 是否影响收入
* 是否影响成本
* 是否违反现有业务流程
* 是否有运营承载能力

---

# 36. Red Team Review

AI 产品经理应主动模拟反方角色：

> “如果我要证明这个方案有问题，我会从哪里攻击？”

重点攻击：

* 用户假设
* 价值假设
* Scope
* 流程
* 状态
* 权限
* Exception
* 依赖
* 商业价值
* 技术成本

---

# 37. 产品 Red Team 问题

```text
如果用户根本没有这个问题呢？

如果用户有问题但不愿改变行为呢？

如果用户只愿意偶尔使用呢？

如果现有解决方案其实已经足够呢？

如果这个 Feature 去掉，核心价值是否仍成立？
```

---

# 38. 流程 Red Team 问题

```text
如果用户中途退出怎么办？

如果操作顺序不同怎么办？

如果上一状态已经变化怎么办？

如果同一个动作执行两次怎么办？

如果系统只完成一半怎么办？
```

---

# 39. AI 产品 Red Team

如果涉及 AI：

```text
AI 输出错误怎么办？

AI 拒绝回答怎么办？

AI 超时怎么办？

AI 每次结果不同怎么办？

用户误信 AI 怎么办？

用户输入敏感内容怎么办？

Provider 挂了怎么办？
```

---

# 40. Review Issue Severity

所有评审问题建议分级。

---

# 41. BLOCKER

定义：

> 不解决就不能进入研发。

典型：

* 核心 Scope 未确定
* 核心流程不闭环
* 关键金额规则未知
* 核心状态冲突
* 法规风险未解决
* 无法定义验收标准

---

# 42. CRITICAL

定义：

> 很可能导致严重业务或研发问题。

例如：

* 权限漏洞
* 重复支付
* 严重数据一致性风险
* 核心 Exception 未定义

原则上研发前解决。

---

# 43. MAJOR

定义：

> 不影响整体方向，但明显影响功能完整性或开发理解。

例如：

* 某次级流程缺失
* 页面状态遗漏
* 规则表达不清

---

# 44. MINOR

定义：

> 小范围体验或文档问题。

例如：

* 文案不一致
* 非核心提示不清晰

---

# 45. SUGGESTION

优化建议。

不阻塞需求。

---

```markdown

### Severity

BLOCKER / CRITICAL / MAJOR / MINOR / SUGGESTION

### Area

Product / UX / Frontend / Backend / QA / Security / Data

### Issue

### Why It Matters

### Evidence

### Recommendation

### Owner

### Status
```

---

# 47. Issue 状态

建议：

```text
Open

In Discussion

Resolved

Accepted Risk

Rejected
```

---

# 48. Accepted Risk

不是所有问题都必须修复。

如果团队明确知道风险，并决定接受：

记录：

```text
Risk

Reason

Impact

Owner

Revisit Condition
```

避免未来出现：

> “当时没人知道。”

---

# 49. Requirement Review 输出

评审结束后建议形成：

```text
Review Summary

Blocking Issues

Critical Issues

Major Issues

Accepted Risks

Decisions

Updated Open Questions

Required PRD Changes

Review Result
```

---

# 50. Review Result

建议只使用清晰状态：

```text
PASS

PASS WITH CONDITIONS

FAIL
```

---

# 51. PASS

表示：

> 无 Blocking / Critical 问题，需求达到交付标准。

---

# 52. PASS WITH CONDITIONS

表示：

> 可以推进部分准备工作，但仍有明确事项必须在开发前完成。

使用时应谨慎。

不要让它变成：

> 实际没评审完，但先开发。

---

# 53. FAIL

表示：

> 当前需求不具备研发条件。

应明确：

* 为什么
* 缺什么
* 返回哪个阶段

---

# 54. Development Readiness

需求评审通过后，还应执行 Development Readiness Check。

核心问题：

> 如果今天把这份需求交给研发，他们是否需要大量猜测才能开始？

如果答案是：

> 是

则还没有 Ready。

---

# 55. Development Readiness Checklist

## Product

* [ ] Why 明确
* [ ] Target User 明确
* [ ] Core Problem 明确
* [ ] Goal 明确
* [ ] MVP Scope 明确
* [ ] Out of Scope 明确

## User Story

* [ ] Core Stories 明确
* [ ] Priority 明确

## Architecture

* [ ] Module Boundary 明确
* [ ] Core Features 明确
* [ ] Dependencies 明确

## Flow

* [ ] Main Flow 闭环
* [ ] Alternative Flow 基本明确
* [ ] Exception Flow 基本明确

## Rule

* [ ] Business Rules 明确
* [ ] Data Rules 明确
* [ ] 没有重大规则冲突

## State

* [ ] 核心 State Machine 明确
* [ ] Forbidden Transition 明确

## Permission

* [ ] Role 明确
* [ ] Resource Scope 明确
* [ ] Action Permission 明确

## UX

* [ ] Page Inventory 完整
* [ ] Core User Flow 明确
* [ ] Key Interaction 明确
* [ ] Critical Page State 明确

## QA

* [ ] Core Acceptance Criteria 可测试
* [ ] Positive / Negative / Boundary 覆盖

## Dependency

* [ ] 外部依赖已确认
* [ ] 关键 Fallback 明确

## Risk

* [ ] 无未解决 BLOCKER
* [ ] 重大 CRITICAL 已解决或明确接受风险

> **READY FOR DEVELOPMENT**

或：

> **NOT READY FOR DEVELOPMENT**

不能使用模糊：

> “差不多可以开发了。”

# 63. 研发 Q&A

研发提问后，产品经理应判断问题属于：

## Requirement Clarification

PRD 没写清楚。

→ 补 PRD。

## New Requirement

研发提出新的业务能力。

→ 进入 Scope Change。

## Technical Design

实现方案问题。

→ 由研发技术设计负责。

## Product Decision

存在多个产品行为方案。

→ 产品经理形成 Decision。

---

# 64. 不要让研发问答只停留在聊天中

如果一个回答会影响：

* Flow
* Rule
* State
* Permission
* Scope
* Acceptance

必须回写正式文档。

---

# 65. Chat Is Not Documentation

不要形成：

```text
“这个问题群里说过。”
```

关键规则应存在于：

> Single Source of Truth。

# 66. 需求拆分

研发交付后通常需要将需求拆解为：

```text
Epic
↓
Feature
↓
User Story
↓
Development Task
```

---

# 67. Epic

Epic 表达较大的产品价值主题。

例如：

> AI 回复辅助。

---

# 68. Feature

例如：

> 基于聊天上下文生成回复。

---

# 69. User Story

例如：

> As a 用户，我希望获得符合当前对话语境的候选回复。

---

# 70. Development Task

技术团队进一步拆：

```text
Frontend Task

Backend Task

Model Integration Task

Database Task

Test Task
```

产品经理不应过度替研发拆具体技术 Task。

---

# 71. Product Breakdown 与 Technical Breakdown

产品负责：

```text
Epic

Feature

User Story

Acceptance Criteria
```

研发负责：

```text
Technical Task

Architecture Task

Implementation Plan
```

# 72. Development Ticket

如果需要创建研发任务，建议包含：

```markdown
# Feature Ticket

## Scope
```

# 73. Ticket 不应复制整个 PRD

研发任务应：

> 包含当前开发需要的上下文。

复杂规则引用 PRD。

不要制造多个彼此容易不一致的“完整版需求”。

---

# 74. Priority

建议明确：

```text
P0
P1
P2
P3
```

或团队已有体系。

优先级必须与：

> MVP Scope / Release

一致。

---

# 75. Priority 不等于开发顺序

某 Feature 是 P0，不一定最先开发。

开发顺序还受：

* Dependency
* Architecture
* Risk
* Parallelization

影响。

具体排期由产品和研发共同决定。

---

# 76. Dependency Mapping

例如：

```text
Authentication
↓
Project
↓
Task
↓
Notification
```

可以帮助研发规划顺序。

---

# 77. Walking Skeleton

对于新产品研发，优先考虑建立：

> 最小端到端主链路。

例如：

```text
用户进入
↓
创建
↓
处理
↓
完成
```

而不是：

> 一个模块 100% 完成后再做下一个。

---

# 78. Vertical Slice

推荐：

> 按用户价值纵向打通。

避免：

```text
第一周只建数据库
第二周只建所有 API
第三周才第一次看到产品
```

具体研发方式由团队决定，但产品可以强调尽早验证完整链路。

# 79. 需求变更

进入开发后出现需求变化：

> 不能直接在聊天里说一句“顺便改一下”。

应进入 Change Control。

# 81. Change 分类

## Clarification

需求本身未变化，只是补清楚。

## Correction

修复原需求错误。

## Scope Change

增加 / 删除能力。

## Rule Change

改变业务逻辑。

## UX Change

改变操作方式。

---

# 82. Clarification 不应伪装成 Scope Change

例如：

原需求：

> 订单取消后释放库存。

研发问：

> 是立即释放吗？

如果产品本意一直如此：

> 属于 Clarification。

---

# 83. Scope Change 必须评估影响

检查：

```text
Design

Frontend

Backend

QA

Schedule

Dependency

Risk
```

---

# 84. Mid-Sprint Change

开发过程中新增需求，应谨慎。

默认问题：

> 为什么不能进入 Next Iteration？

除非：

* BLOCKER
* 法规
* 严重线上风险
* 核心需求理解错误

---

# 85. Gold Plating

研发有时会说：

> “顺便把以后要用的也做了。”

产品也可能说：

> “顺便加个按钮。”

都需要警惕。

Gold Plating 会增加：

* Scope
* Cost
* QA
* Complexity

---

# 86. Product Debt

如果为了 MVP 暂时采用简化方案，可以显式记录 Product Debt。

例如：

```text
当前：
只支持单管理员。

未来：
支持多管理员与细粒度权限。
```

避免未来团队误以为：

> 当前方案就是长期设计。

---

# 87. Technical Constraint Feedback

开发过程中如果出现技术约束：

```text
原设计无法实现
成本远超预期
性能达不到
第三方能力受限
```

应该：

```text
Technical Finding
↓
Product Impact
↓
Alternative Options
↓
Product Decision
```

---

# 88. 不让技术细节偷偷改变产品

例如研发自行决定：

> “这个太难了，所以错误时就直接返回首页。”

这实际上是 Product Behavior Change。

应由产品确认。

---

# 89. Implementation Review

对于高风险 Feature，在开发实施方案确定后，产品可快速确认：

> 技术方案有没有改变产品语义？

产品不需要 Review 代码。

---

# 90. Acceptance During Development

开发完成后，产品验收不是：

> 页面能打开。

而应基于：

> Acceptance Criteria。

---

# 91. Product Acceptance

重点确认：

* Core User Flow
* Business Rule
* State
* Permission
* Exception
* User Feedback
* Scope

---

# 92. QA 与 Product Acceptance 区别

QA：

> 系统是否符合规格。

Product：

> 产品是否符合预期价值和产品设计。

两者都重要。

---

# 93. Pre-Release Requirement Check

上线前建议再次确认：

```text
Scope 是否完整

Critical Bugs 是否解决

Tracking 是否可用

Permission 是否正确

Fallback 是否准备

运营是否准备

Support 是否知道新功能
```

---

# 94. Release Scope

上线前形成最终：

```text
Shipped

Not Shipped

Known Issues

Accepted Risks
```

防止：

> “大家以为这个版本有，实际上没做。”

---

# 95. Known Issues

允许带已知问题上线时，必须明确：

* 问题
* 影响
* Workaround
* 风险
* 后续计划

---

# 96. Rollback / Disable Requirement

关键功能可以考虑：

> 如果上线出现重大问题，能否关闭该能力？

尤其：

* AI
* 支付
* 推荐
* 新算法
* 高风险自动化

产品层只需明确需要有安全停止能力。

具体实现由研发设计。

---

# 97. Feature Flag

如果项目有较大风险，可提出产品需求：

> 需要支持分批开放 / 灰度。

不必规定使用哪种技术实现。

# 98. Gradual Rollout

可以考虑：

```text

↓

↓

↓
50%
↓
100%
```

是否需要取决于风险。

# 120. 最终工作原则

需求评审的价值不是：

> 多开一次会议。

而是：

> **在最便宜的阶段发现最昂贵的问题。**

研发交付的价值不是：

> 把 PRD 从产品经理手里扔给研发。

而是：

> **让研发在理解产品目标、范围、规则和风险的基础上开始实施。**

始终牢记：

> PRD 完成 ≠ 可以开发。

> 原型完成 ≠ 需求完整。

> Happy Path 跑通 ≠ 业务逻辑完整。

> 研发能看懂 ≠ QA 能测试。

> 没人提出问题 ≠ 没有问题。

> Review 的目标不是通过，而是发现问题。

> Handoff 的目标不是交文件，而是交付清晰的产品决策。

最终要建立：

```text
PRD
↓
Requirement Review
↓
Issue Resolution
↓
Development Readiness
↓
Development Handoff
↓
Implementation
```

并且只有真正满足：

```text
Why Clear
Who Clear
Scope Clear
Flow Closed
Rule Clear
State Clear
Permission Clear
Exception Covered
Acceptance Testable
Risk Known
```

时，才正式给出：

> **READY FOR DEVELOPMENT**
