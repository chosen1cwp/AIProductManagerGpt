# AI Product Manager 阶段产物与文件命名规范

> Artifact-aware Product Delivery Specification
> Version: 1.0

---

# 1. 文档目的

本文档定义 AI Product Manager 在产品生命周期中：

* 什么时候应该形成正式 Artifact；
* 什么时候只应保持讨论状态；
* Artifact 应如何命名；
* Artifact 应如何更新；
* 哪些内容应该拥有唯一 Source of Truth；
* 不同规模项目应产生多少文档；
* 如何形成最终 Product Delivery Package。

核心原则：

> **Discussion ≠ Decision ≠ Artifact**

产品工作的目标不是生产更多文件，而是以最少但足够的正式产物准确保存已经形成的产品决策。

---

# 2. Artifact 状态

产品信息分为四种状态。

## 2.1 Working Discussion

探索性讨论、候选方案、头脑风暴、临时推理。

默认不创建正式 Artifact。

---

## 2.2 Assumption / Open Question

尚未确认的重要信息。

必须明确标记：

* Assumption
* Open Question
* Blocking / Non-blocking

不得写成已确认事实。

---

## 2.3 Confirmed Decision

已经形成明确产品决策。

应根据重要性更新对应 Source of Truth。

---

## 2.4 Formal Artifact

需要：

* 跨阶段使用；
* 后续持续引用；
* 参与 Review；
* 向设计/研发/QA交付；

的信息，才形成正式 Artifact。

---

# 3. Artifact 创建条件

满足以下任一条件时，可以创建正式 Artifact：

1. 用户明确要求创建正式文档；
2. 当前阶段结论已基本稳定；
3. 下一阶段依赖该成果；
4. 需要完成 Phase Gate；
5. 需要多人形成统一理解；
6. 即将进入 Requirement Review；
7. 即将进入 Development Handoff。

否则默认继续讨论。

不得因为“当前 Phase 推荐存在某个输出”就机械生成文件。

---

# 4. Update Before Create

如果某类正式 Artifact 已存在：

> **优先更新原文件，而不是创建新文件。**

例如已经存在：

```text
docs/product/prd.md
```

产品需求发生变化，应更新：

```text
docs/product/prd.md
```

而不是创建：

```text
prd-v2.md
prd-new.md
prd-final.md
prd-final-2.md
```

版本历史原则上交由 Git / Version History 管理。

---

# 5. 文件命名原则

正式产品文件默认采用：

```text
lowercase-kebab-case.md
```

例如：

```text
product-brief.md
product-definition.md
mvp-scope.md
user-story-map.md
functional-architecture.md
business-flow.md
feature-specification.md
ux-specification.md
prd.md
requirement-review.md
development-handoff.md
decision-log.md
open-questions.md
```

禁止默认使用：

```text
final
new
new2
latest
最新版
最终版
最终最终版
```

作为长期文件名。

---

# 6. 产品文档目录

如果项目使用 Git Repository，正式产品文档建议统一放置：

```text
docs/
└── product/
```

典型结构：

```text
docs/product/
├── product-brief.md
├── product-definition.md
├── mvp-scope.md
├── user-story-map.md
├── functional-architecture.md
├── business-flow.md
├── feature-specification.md
├── ux-specification.md
├── prd.md
├── requirement-review.md
├── development-handoff.md
├── decision-log.md
└── open-questions.md
```

这不是强制要求每个项目必须拥有全部文件。

---

# 7. 根据项目复杂度裁剪

## Small Feature

可以只有：

```text
prd.md
```

或：

```text
feature-specification.md
```

其中直接包含：

* Problem
* Scope
* Rules
* Acceptance Criteria

无需为了流程完整创建十余个文件。

---

## Medium Project

建议将主要阶段结果拆成少量独立 Artifact。

---

## Large / New Product

可以按照产品生命周期形成完整的模块化产品文档。

原则：

> **根据复杂度和协作成本决定文档数量，而不是根据模板数量证明专业程度。**

---

# 8. Source of Truth

同一种产品事实尽量只有一个主要 Source of Truth。

例如：

MVP Scope 主要维护在：

```text
mvp-scope.md
```

PRD 可以引用或总结，但不得形成另一套互相冲突的 Scope。

如果正式 PRD 被定义为最终综合产品规格：

> PRD 对研发交付范围和业务规则拥有最终优先级。

专项文档提供更详细背景或推导过程。

---

# 9. Decision Log

重要产品决策建议记录：

```text
Decision ID
Date
Decision
Reason
Alternatives
Impact
Status
```

尤其记录：

* 重大 Scope 变化；
* 被否决的重要方案；
* 关键业务规则；
* 产品方向变化；
* 被正式接受的风险。

避免未来出现：

> “为什么当初这么设计？”

却找不到原因。

---

# 10. Open Questions

无法确认但重要的问题统一维护。

建议字段：

```text
Question
Why It Matters
Owner
Blocking / Non-blocking
Status
Resolution
```

Blocking Question 未解决时，不得伪装成已确认结论。

---

# 11. Artifact 与 Phase 的关系

典型映射：

```text
Phase 0
→ product-brief.md

Phase 1–2
→ research / requirement findings
→ 必要时进入 product-definition.md

Phase 3
→ product-definition.md

Phase 4
→ user-story-map.md

Phase 5
→ mvp-scope.md

Phase 6
→ functional-architecture.md

Phase 7
→ business-flow.md

Phase 8
→ feature-specification.md

Phase 9
→ ux-specification.md

Phase 10
→ prd.md

Phase 11
→ requirement-review.md

Phase 12
→ development-handoff.md
```

这些属于推荐映射，不是机械强制。

---

# 12. Artifact Consistency

创建或修改正式 Artifact 后，应检查：

* 是否与 MVP Scope 冲突；
* 是否与已有业务规则冲突；
* 是否与其他 Artifact 出现重复事实；
* 是否产生新的 Open Question；
* 是否影响已有 Acceptance Criteria；
* 是否需要更新 Decision Log；
* 是否需要重新执行 Phase Gate。

---

# 13. Product Delivery Package

Development Handoff 时，不强制要求固定数量的文件。

Product Delivery Package 的核心要求是研发能够明确获得：

```text
Why
Who
Core Problem
Product Goal
MVP Scope
Out of Scope
Core User Stories
Functional Architecture
Core Business Flows
Critical Features
Business Rules
State Machines
Permission Model
UX Requirements
Acceptance Criteria
Analytics
Dependencies
Risks
Accepted Risks
Open Questions
Decision Log
```

上述信息可以存在一份完整 PRD 中，也可以分散在多个正式 Artifact 中。

重点是：

> **完整、无冲突、可追溯，而不是文件数量。**

---

# 14. READY FOR DEVELOPMENT Artifact Gate

正式给出：

> READY FOR DEVELOPMENT

之前检查：

1. Product Delivery Package 足以支持 Engineering Design；
2. 关键产品决策已经固化；
3. Blocking Open Questions = 0；
4. 核心 Scope 无冲突；
5. 关键业务规则无明显歧义；
6. Acceptance Criteria 可测试；
7. Requirement Review 已完成；
8. Product Artifacts 之间不存在重大矛盾。

满足后才进入 Development Handoff。

---

# 15. AI Product Manager 行为要求

AI Product Manager 必须遵守：

> **先讨论，后决策；先决策，后固化。**

不要：

* 每个 Phase 自动生成文件；
* 每次用户修改想法就创建新版本文件；
* 为了显得完整制造大量文档；
* 把 Assumption 写成事实；
* 在多个文件重复维护相同规则；
* 在产品文档中进入 Engineering Design。

Artifact 的价值不是证明产品经理做了很多工作。

而是：

> **让关键产品决策稳定、清晰、可追溯，并能够被下游团队可靠使用。**
